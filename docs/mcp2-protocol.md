# MUD Client Protocol (MCP) 2.1 — Reference

Source: https://www.moo.mud.org/mcp/mcp2.html

> **Note:** In this project "MCP" always refers to the MUD Client Protocol, not any LLM-related protocol.

---

## Overview

MCP 2.1 is a standardized out-of-band message format for MUD environments. It enables structured application-level communication between client and server over a single network connection without interfering with ordinary in-band MUD output.

Design principles:
- Operates in 7-bit ASCII
- Minimal distinction between client and server roles
- Defines message *format*, not application semantics — individual packages define what messages mean
- State management delegated to application-specific packages

---

## Line Classification

Every line received must be classified before display or processing:

| Line prefix | Meaning | Action |
|---|---|---|
| `#$#` | Out-of-band MCP message | Parse and dispatch; never display |
| `#$"` | Quoted in-band line | Strip prefix, display remainder |
| anything else | In-band content | Display as-is |

When **sending** in-band content that happens to start with `#$#` or `#$"`, the sender must prefix it with `#$"` to prevent the receiver from misclassifying it.

---

## Message Format

### Simple (single-line) message

```
#$# message-name auth-key keyword: value keyword: value ...
```

- `message-name` — identifies the message type (case-insensitive)
- `auth-key` — the session authentication key (case-sensitive); absent only on the initial `mcp` handshake message from the server
- `keyword: value` pairs — argument list (keywords are case-insensitive, values preserve case)

### Value quoting

Values that contain spaces or special characters must be double-quoted:

```
#$#mcp-edit-set 1234 name: "My Verb" content*: foo123
```

Unquoted values must match `[^ \t"*:]+`. All others must be quoted.

### Multiline values

A keyword suffixed with `*` signals a multiline value. The value on the same line is a **data-tag** (unique identifier for this multi-line block). Subsequent lines prefixed with `#$#*` carry the data, and `#$#:` closes the block:

```
#$#mcp-edit-set 1234 name: foo content*: dt42
#$#* dt42 content: first line of content
#$#* dt42 content: second line of content
#$#: dt42
```

A single message may have multiple multiline fields, each using a different data-tag. The closing `#$#:` indicates the entire message (not just one field) is complete.

## Startup / Handshake Sequence

### Step 1 — Server sends `mcp`

The server initiates MCP by sending (no auth key on this message):

```
#$#mcp version: 2.1 to: 2.1
```

Fields:
- `version:` — minimum MCP version the server supports
- `to:` — maximum MCP version the server supports

### Step 2 — Client responds with `mcp`

The client replies with its own version range and generates a session auth key:

```
#$#mcp authentication-key: <key> version: 2.1 to: 2.1
```

Fields:
- `authentication-key:` — client-generated random string; used to authenticate all subsequent messages in this session
- `version:` / `to:` — client's supported version range

### Version negotiation algorithm

1. If the server's range and the client's range do not overlap → MCP is not used; ignore all subsequent `#$#` lines.
2. If they overlap → the negotiated version is the **highest version present in both ranges**.

### Auth key

- Generated by the client; a random opaque string (no cryptographic guarantees, but prevents casual spoofing)
- Appears in cleartext on every subsequent message
- Implementations must validate the key on every received message and silently drop messages with invalid keys

## Package Negotiation (`mcp-negotiate`)

After the initial handshake, capabilities are exchanged using the `mcp-negotiate` package (version 2.0; minimum 1.0 required).

### `mcp-negotiate-can`

Advertises a package the sender supports:

```
#$#mcp-negotiate-can <auth-key> package: <package-name> min-version: <ver> max-version: <ver>
```

Example:
```
#$#mcp-negotiate-can 1234 package: mcp-edit min-version: 1.0 max-version: 1.0
#$#mcp-negotiate-can 1234 package: mcp-cord min-version: 1.0 max-version: 2.0
```

- Both sides send `mcp-negotiate-can` for each package they support
- A package is **mutually supported** once both sides have advertised compatible version ranges
- You may begin using a package as soon as mutual support is established (no need to wait for `mcp-negotiate-end`)

### `mcp-negotiate-end`

Signals that the sender has finished advertising packages:

```
#$#mcp-negotiate-end <auth-key>
```

- Allows a receiver to finalize package selection when multiple overlapping packages serve the same purpose
- **Critical rule:** An implementation must **not** delay sending its own `mcp-negotiate-can` messages until after receiving `mcp-negotiate-end`; the exchange is concurrent

### Package version negotiation

Same algorithm as protocol version negotiation: if version ranges overlap, use the highest common version.

## Cord Support (`mcp-cord`)

The `mcp-cord` package multiplexes secondary logical channels (cords) over the single MCP connection. This allows bidirectional messaging between specific server and client objects.

### Cord IDs

- Server-created cord IDs begin with `I` (e.g., `I12345`)
- Client-created cord IDs begin with `R` (e.g., `R00042`)
- IDs must be unique within a session

### `mcp-cord-open`

Opens a new cord:

```
#$#mcp-cord-open <auth-key> _id: <cord-id> _type: <type>
```

Example:
```
#$#mcp-cord-open 3487 _id: I12345 _type: whiteboard
```

- `_type` identifies the application-level protocol for this cord
- The underscore prefix on `_id` and `_type` is part of the keyword name

### `mcp-cord`

Sends a message along an existing cord:

```
#$#mcp-cord <auth-key> _id: <cord-id> _message: <msg-name> [keyword: value ...]
```

Example:
```
#$#mcp-cord 3487 _id: I12345 _message: draw color: red x: 10 y: 20
```

Additional keyword-value pairs are specific to the message type defined by the cord's `_type`.

### `mcp-cord-closed`

Signals that the sender is closing the cord:

```
#$#mcp-cord-closed <auth-key> _id: <cord-id>
```

- One-directional signal; no acknowledgement is expected
- After sending, the sender should stop using the cord; the receiver may also stop

## Message Name and Keyword Rules

- Message names: case-insensitive, conventionally lowercase, hyphen-separated
- Keywords: case-insensitive, always end with `:` (the colon is part of the keyword token in the wire format)
- Auth key: case-sensitive
- Values: preserve original case
- Package-specific messages should be prefixed with the package name: e.g., `mcp-edit-set` belongs to the `mcp-edit` package

---

## Package Naming Conventions

| Prefix | Ownership |
|---|---|
| `mcp-` | Reserved for specification-defined packages |
| `dns-org-example-*` | Organizational packages (reversed DNS) |
| (other) | Reserved for future naming authority assignment |

---

## Error Handling

- **Invalid/unknown messages:** silently drop, or notify the user unobtrusively
- **Unknown extra arguments on a known message:** tolerate and ignore
- **Auth key mismatch:** silently drop the message
- **Overlapping version ranges absent:** disable MCP for the session
- Debugging/verbose mode may log dropped messages for diagnostics
